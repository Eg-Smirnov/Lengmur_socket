# Команды и ответы

JSON-команды передаются в UTF-8 внутри Serial-кадра типа 0 и не завершаются
переводом строки. Ответ ESP32 передаётся кадром типа 1.

Размер сериализованной JSON-команды или JSON-ответа ограничен 256 байтами, хотя
двоичный формат кадра допускает payload до 2048 байт. Клиент проверяет размер
UTF-8-представления команды до отправки. На корректный кадр с JSON-командой
размером больше 256 байт прошивка отвечает:

```json
{"ok":false,"error":"request_too_large"}
```

## Содержимое по типам кадров

| Тип кадра | Направление | Что передаётся |
| ---: | --- | --- |
| 0 | клиент → ESP32 | JSON-команды `get`, `set` и `start_sweep` (UTF-8) |
| 1 | ESP32 → клиент | JSON-ответы на команды и незапрошенные сообщения телеметрии |
| 2 | ESP32 → клиент | бинарный результат завершённого одиночного sweep |

Типы 3…7 не используются. Формат заголовка, CRC и бинарного payload типа 2
описан в [документе Serial-транспорта](serial.md).

### Команды типа 0

| Команда | Назначение | Пример |
| --- | --- | --- |
| `get` | Прочитать всю конфигурацию или одно поле | `{"op":"get","field":"sample_rate"}` |
| `set` | Записать поле или полную конфигурацию | `{"op":"set","field":"sample_rate","value":1000}` |
| `start_sweep` | Запустить один sweep | `{"op":"start_sweep"}` |

Для чтения всей конфигурации отправьте `{"op":"get"}`. Полную конфигурацию
можно записать объектом `config`, например:

```json
{"op":"set","config":{"sample_rate":1000,"min_voltage":-10,"max_voltage":10,"shunt_res":0}}
```

### Сообщения типа 1

| Ситуация | Формат payload |
| --- | --- |
| Успешный `set` или принятый `start_sweep` | `{"ok":true}` |
| Успешный `get` всего объекта | `{"ok":true,"config":{...}}` |
| Успешный `get` одного поля | `{"ok":true,"field":"sample_rate","value":1000}` |
| Ошибка | `{"ok":false,"error":"код"}` |
| Периодическая телеметрия покоя | `{"type":"telemetry","voltage":<int16>,"current":<int16>}` |

Телеметрия отправляется примерно раз в 500 мс. Она не является ответом на
команду, поэтому клиенту нужно читать кадры типа 1 непрерывно и различать
телеметрию и ответы по содержимому JSON.

### Данные типа 2

Кадр типа 2 отправляется отдельно после успешного завершения `start_sweep`.
Payload содержит число точек `uint16` little endian, затем для каждой точки —
код напряжения и код тока `int16` little endian. Максимум — 100 точек. Точные
смещения полей и условия сбора приведены в [документе Serial-транспорта](serial.md).

## Последовательность обмена

Прикладной протокол пока не содержит идентификатора запроса. Клиент должен
отправлять следующий запрос только после получения ответа на предыдущий либо
после истечения его тайм-аута. Одновременное ожидание нескольких ответов не
поддерживается.

Это ограничение не требует от прошивки немедленно сформировать ответ в той же
итерации `ControlTask`: запрос и соответствующий ответ могут последовательно
обрабатываться через локальную очередь и межъядерную транзакцию. Для нескольких
одновременных запросов в будущем потребуется расширить прикладной протокол
идентификатором.

## Настройки

Чтение всей конфигурации или отдельного поля, запись отдельного поля или полного
объекта, а также запуск sweep выполняются такими JSON-командами:

```json
{"op":"get"}
{"op":"get","field":"sample_rate"}
{"op":"set","field":"sample_rate","value":1000}
{"op":"set","config":{"sample_rate":1000,"min_voltage":-10,"max_voltage":10,"shunt_res":0}}
{"op":"start_sweep"}
```

`start_sweep` подтверждается JSON-ответом `{"ok":true}`. Если сбор уже идёт
или настройки измерения недопустимы, возвращается `sweep_busy_or_invalid_config`.
ESP32 ждёт попадания сырого signed-кода напряжения в включительный диапазон
`min_voltage…max_voltage`, затем собирает точки с частотой `sample_rate` до
выхода напряжения из диапазона или до 100 точек. Результат приходит отдельным
кадром типа 2; формат описан в [документе Serial](serial.md).

В режиме `Idle` примерно раз в 500 мс отправляется JSON-телеметрия типа 1 с
сырыми кодами напряжения и тока. После принятия `start_sweep` и до завершения
передачи результата телеметрия приостанавливается, включая ожидание входа
напряжения в заданное окно. Двоичный кадр результата описан в
[документе Serial](serial.md).

При `set` прошивка передаёт настройки задаче измерительного тракта, применяет их
на Core 0, сохраняет в NVS и только после межъядерного commit возвращает
успешный ответ. В текущем состоянии `Idle` это происходит сразу; после появления
sweep-сбора изменение будет ожидать границы sweep. Числовому значению `0`
соответствует автоматический выбор; сейчас он выбирает шунт 10 МОм.

Состав и типы полей определены в [`config.json`](../../config.json) и описаны в
[разделе конфигурации](../firmware/configuration.md).

## Результат выполнения

Успешный ответ содержит поле `"ok":true`. Ошибка имеет вид:

```json
{"ok":false,"error":"код"}
```

Ошибки кадра и очереди возвращаются тем же форматом:

| Код | Причина |
| --- | --- |
| `invalid_crc` | CRC32 принятого кадра не совпадает с вычисленной |
| `unsupported_version` | кадр использует неподдерживаемую версию |
| `unexpected_packet_type` | входящий кадр имеет тип, отличный от команды |
| `request_too_large` | JSON-payload корректного кадра превышает 256 байт |
| `queue_full` | готовое событие или межъядерная команда не поместились в свою очередь |
| `sweep_busy_or_invalid_config` | sweep уже выполняется или конфигурация sweep некорректна |
| `measurement_failed` | драйвер АЦП не смог прочитать пару каналов |

Формат внешнего кадра описан в [документе Serial-транспорта](serial.md).

Команды прежних диагностических прототипов `measure_once`, `get_out_state` и
`toggle_out` текущей прошивкой не поддерживаются.
