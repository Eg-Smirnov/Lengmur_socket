# Архитектура прошивки

Этот документ фиксирует двухъядерную модель исполнения прошивки. Реализация
использует USB Serial, idle-телеметрию и тестовый одиночный sweep; Ethernet и
постоянная серия sweep пока не входят в текущий этап.

## Ограничения текущего этапа

- Одновременно активны только один транспорт и один клиент.
- Транспорт выбирается целиком: обмен идёт либо через Serial, либо через
  будущий TCP-транспорт.
- Переключение между транспортами и судьба незавершённой работы старого
  транспорта будут определены при добавлении второго транспорта.
- На Core 1 работает явная `ControlTask`, а на Core 0 — явная
  `AcquisitionTask`. Стандартная Arduino `loopTask` не обслуживает компоненты
  приложения и только периодически уступает процессор.
- Существующие Serial-кадры, JSON-команды, ответы и коды ошибок должны остаться
  совместимыми.
- Драйверы измерительного тракта доступны только `AcquisitionTask`; транспорт,
  кодек, прикладной диспетчер, JSON-конфигурация и NVS доступны только
  `ControlTask`.

## Состояние реализации

Реализован путь Serial-запроса через `ControlTask`, `SerialTransport`, общий
`FrameCodec`, локальную очередь `AppEventQueue` и `CommandDispatcher`.
Диспетчер обрабатывает события
`ProcessTransportRequest`, `SendTransportResponse`, `InvalidCrc`,
`UnsupportedVersion`, `UnexpectedPacketType` и `RequestTooLarge`.

Поддерживаются операции конфигурации `get` и `set`, а также `start_sweep` для
одиночного sweep. Формат передаваемого результата описан в
[`../protocols/serial.md`](../protocols/serial.md).
`AcquisitionTask` опрашивает пару AD7322 с частотой 2 Гц в покое, ждёт входа
сырого кода напряжения в заданное окно и записывает не более 100 пар с частотой
`sample_rate`. По завершении Core 1 отправляет бинарный кадр типа 2.
`set` выполняется асинхронно между ядрами и завершается двухфазным подтверждением.

## Задачи FreeRTOS и владение ресурсами

| Задача | Ядро | Приоритет | Начальный стек | Ответственность |
| --- | ---: | ---: | ---: | --- |
| `ControlTask` | 1 | 2 | 8192 байт | Serial, кодек, диспетчер, конфигурация и NVS |
| `AcquisitionTask` | 0 | 3 | 4096 байт | ADG5408, пара AD7322, телеметрия и буфер одного sweep |

`ControlTask` читает не более 64 байт Serial за одну итерацию, чтобы приём
длинного кадра не вытеснял обработку межъядерных результатов. После итерации она
задерживается на один тик FreeRTOS. `AcquisitionTask` принимает команды с
тайм-аутом один тик, обслуживает телеметрию и сбор точек в своей задаче.

Все обращения к ADG5408 выполняются с Core 0. `Serial.begin()` вызывается из
`ControlTask` на Core 1. Пользовательских ISR пока нет; новые коммуникационные
обработчики должны устанавливаться с Core 1, записывать только в заранее
выделенный буфер или уведомлять задачу и не выполнять разбор либо вычисления в
контексте прерывания.

## Компоненты и поток данных

`esp.ino` только запускает верхний уровень приложения. `Application::begin()`
создаёт `ControlTask`, а Arduino `loop()` после этого не обслуживает приложение:

```cpp
Application application;

void setup() {
  application.begin();
}

void loop() {
  delay(1000);
}
```

Основной поток входящего запроса:

```text
Application вызывает активный транспорт
        ↓
транспорт читает байты и вызывает декодер кадров
        ↓
декодер помещает готовое событие в общую очередь
        ↓
Application передаёт управление диспетчеру
        ↓
диспетчер извлекает и обрабатывает событие
        ↓
хранилище конфигурации / сбор данных / управление выходом
        ↓ команда ответа и JSON-payload
общая очередь приложения
        ↓
диспетчер передаёт событие ответа активному транспорту
        ↓
транспорт вызывает кодировщик кадров и записывает байты
```

Транспорт отвечает за чтение и запись байтов и непосредственно использует общий
кодек кадров. На входе транспорт передаёт принятые байты декодеру, а на выходе
передаёт готовый прикладной payload кодировщику. Вызов кодировщика находится
внутри транспорта, а не в `Application` или диспетчере.

Кодек хранит единственное состояние разбора потока, проверяет кадры и помещает в
общую очередь только готовые события. Сырые байты и промежуточные части кадра не
проходят через диспетчер и общую очередь приложения. В будущем тот же экземпляр
кодека может обслуживаться другим активным транспортом.

Диспетчер вызывается `ControlTask` и обрабатывает элементы локальной очереди
Core 1. Он не описывается непосредственно в `esp.ino`, не работает с потоком
байтов и не вызывает кодек. При обработке
`SendTransportResponse` диспетчер вызывает операцию отправки активного
транспорта с готовым прикладным payload.

Одна итерация `ControlTask` концептуально имеет вид:

```cpp
void Application::runControlTask() {
  processAcquisitionResults();
  dispatcher_.processPendingAcquisition();
  transport_.process(event_queue_);
  dispatcher_.processOne(event_queue_, transport_);
}
```

Конкретные сигнатуры могут измениться при реализации, но направление вызовов и
границы ответственности должны сохраниться. Транспорт получает доступ к общему
кодеку при создании или выборе активного транспорта и использует его внутри
своих операций `process()` и отправки.

## Общая очередь приложения

Очередь принадлежит `ControlTask` и не является межъядерной. Через неё проходят
сообщения транспорта и короткие внутренние события Core 1. Результаты
`AcquisitionTask` сначала принимаются из отдельной FreeRTOS-очереди и только
затем при необходимости преобразуются в локальные события.

Элемент очереди содержит небольшой статический payload:

```cpp
constexpr size_t kAppEventPayloadSize = 256;

struct AppEvent {
  AppCommand command;
  uint16_t payload_size;
  alignas(4) uint8_t payload[kAppEventPayloadSize];
};
```

Payload может быть пустым. Его формат определяется значением `command`, поэтому
отдельные универсальные признаки вида payload и универсальный дескриптор данных
не вводятся. Получатель обязан проверить `payload_size` перед извлечением
структуры соответствующей команды.

Внутренние структуры копируются в payload и извлекаются из него через `memcpy`
после проверки размера. Наследование, виртуальные объекты и размещение дочерних
объектов непосредственно в очереди не используются.

Большинство команд и ответов занимают несколько десятков байт. Размер 256 байт
позволяет хранить существующие JSON-команды и ответы с запасом, но не резервирует
максимальные 2048 байт транспортного payload в каждом слоте. Восемь элементов
занимают около 2 КБ SRAM без учёта небольших накладных расходов очереди.

Начальный набор команд:

```cpp
enum class AppCommand : uint8_t {
  ProcessTransportRequest,
  SendTransportResponse,
  InvalidCrc,
  UnsupportedVersion,
  UnexpectedPacketType,
  RequestTooLarge,
  ProcessAcquiredData,
  ProcessStoredSweep,
  SendSweepData,
  SendStoredSweep,
  StartMeasurement,
  StopMeasurement,
};
```

`ProcessTransportRequest` начинает двусторонний обмен: диспетчер разбирает JSON
из payload, выполняет команду и помещает результат обратно в очередь как
`SendTransportResponse`. При обработке этого события диспетчер передаёт готовый
payload активному транспорту. Транспорт сам вызывает кодировщик кадров и
отправляет получившиеся байты клиенту. Диспетчер не работает с байтами кадра и
не вызывает кодировщик непосредственно.

Ошибки кадрирования представлены командами той же очереди. Их обработка также
создаёт `SendTransportResponse`. Внутренние команды не обязаны создавать
транспортный ответ; это определяется видом команды.

Очередь статическая, работает как FIFO и содержит восемь элементов. Семь слотов
доступны всем локальным событиям, последний зарезервирован для
`SendTransportResponse`, чтобы асинхронное завершение операции не осталось без
ответа. Один элемент занимает 260 байт, вся полезная область очереди — 2080
байт. После реализации прошивка использует 26652 байта глобальной динамической
памяти из 327680 байт при сборке для ESP32-WROOM-32.

## Размер payload и буферы

Для транспорта и очереди действуют разные пределы:

```cpp
constexpr size_t kMaxFramePayloadSize = 2048;
constexpr size_t kAppEventPayloadSize = 256;
```

Первый предел относится к payload кадра и позволяет передавать бинарные данные.
Второй относится к JSON-командам, JSON-ответам и внутренним событиям общей
очереди. Крупные массивы измерений через очередь не копируются.

Входящая JSON-команда размером больше 256 байт, но не больше допустимого размера
кадра, полностью принимается и проверяется кодеком. После успешной проверки CRC
её содержимое не помещается в очередь; вместо него создаётся пустое событие
`RequestTooLarge`, которое приводит к JSON-ответу с ошибкой
`request_too_large`. Клиент должен проверять размер JSON до отправки.

Для исходящего сообщения диспетчер формирует JSON-payload и помещает его в
очередь как `SendTransportResponse`. При обработке этого элемента payload
передаётся транспорту, а транспорт вызывает кодировщик для вычисления заголовка
и CRC. После этого транспорт может последовательно отправить заголовок, payload
и CRC без выделения второго буфера полного кадра.

## Сырые данные и sweep

Режим сбора определяет вид события и место хранения данных.

В конечном режиме без накопления отдельный канал сырых данных передаёт небольшую
порцию из Core 0 обработчику Core 1. Только после перехода на Core 1 она может
быть преобразована в локальную команду `ProcessAcquiredData`, затем в
`SendSweepData` и отправлена бинарным пакетом.

В длительном режиме сборщик накапливает очередной полный sweep, записывает его
во Flash и помещает в очередь `ProcessStoredSweep`. Payload этой команды
содержит только сведения о записи: логический идентификатор или смещение в
выделенной области Flash, число точек и необходимые параметры формата.
Абсолютный физический адрес Flash в интерфейсах приложения не используется,
чтобы разметка памяти оставалась внутренней деталью хранилища.

После обработки `ProcessStoredSweep` создаётся `SendStoredSweep` с теми же
сведениями о записи. Компонент отправки читает данные непосредственно из Flash;
полный sweep не копируется через общую очередь. Форматы payload у
`ProcessAcquiredData`, `ProcessStoredSweep`, `SendSweepData` и
`SendStoredSweep` различаются и однозначно задаются самой командой.

Формат записей во Flash, размер выделенной области, восстановление после
незавершённой записи и политика освобождения старых sweep будут определены в
отдельной задаче реализации длительного сбора.

## Итерация ControlTask

Порядок одного прохода:

1. Извлечь все доступные результаты `AcquisitionTask`.
2. Повторить отложенную отправку `commit` или `rollback`, если она ещё не
   попала в межъядерную очередь.
3. Принять из активного транспорта не более 64 байт и передать их кодеку.
4. Поместить завершённые кадры и обнаруженные ошибки в локальную очередь.
5. Извлечь и обработать не более одного элемента локальной очереди.
6. Уступить процессор на один тик FreeRTOS.

Обработка `ProcessTransportRequest` и ошибок кадра создаёт в очереди
`SendTransportResponse`. Сам ответ отправляется при извлечении этого элемента в
одной из следующих итераций. Таким образом, входящие запросы, внутренние команды
и исходящие ответы проходят через одну очередь.

Обработка одного элемента за проход регулярно возвращает управление приёму
байтов. Ограничивать число читаемых за проход байтов пока не требуется.

## Межъядерный обмен

Команды Core 1 → Core 0 и результаты Core 0 → Core 1 передаются через две
отдельные очереди FreeRTOS ёмкостью по четыре элемента. Сообщения содержат тип,
идентификатор транзакции и, где требуется, копию `AcquisitionConfig`.
Указатели на изменяемые или временные данные между ядрами не передаются.

У каждой очереди один производитель и один потребитель. `ControlTask` никогда не
ожидает места для начальной команды: если `PrepareConfig` поставить невозможно,
клиент получает существующую ошибку `queue_full`. После принятия prepare в
очереди гарантированно освобождён слот для решения `commit` или `rollback`; если
он временно недоступен, управляющая задача повторяет отправку в следующих
итерациях. `AcquisitionTask` публикует результат с обратным давлением и в это
время не начинает новую работу.

Будущие сырые отсчёты должны использовать отдельный канал. Они не могут занять
место управляющих сообщений или ответов. Переполнение канала отсчётов означает
`overrun`: незавершённый sweep отбрасывается, сбор останавливается, а состояние
гарантированно передаётся на Core 1. Отбрасывание отдельных старых или новых
точек запрещено.

## Обработка прерываний

Обработчик аппаратного прерывания в такой схеме должен выполнять только
минимальную работу: складывать принятые байты в системный или кольцевой буфер и
уведомлять транспортную задачу. Разбор кадров, вычисление CRC и создание событий
выполняются после выхода из прерывания:

```text
прерывание транспорта
→ входной буфер и уведомление
→ транспортная задача вызывает кодек
→ кодек помещает готовое событие в потокобезопасную очередь
→ диспетчер обрабатывает событие
```

Коммуникационные ISR уведомляют `ControlTask` на Core 1. Если для sweep-сбора
потребуется отдельный измерительный ISR, его привязка будет определена вместе с
реализацией периодического чтения AD7322. Буферы для ISR выделяются до запуска
измерения; общая прикладная очередь из ISR не используется.

## Ошибки кадров

- Байты до сигнатуры кадра молча отбрасываются.
- Полный кадр с неверной контрольной суммой создаёт команду `InvalidCrc`, после
  чего повреждённый кадр отбрасывается и поиск сигнатуры продолжается.
- Кадр поддерживаемого размера с корректной CRC, но другой версией создаёт
  `UnsupportedVersion`.
- Кадр с корректной CRC, но неподдерживаемым типом создаёт
  `UnexpectedPacketType`.
- Ошибка переполнения очереди не может быть помещена в заполненную очередь и
  поэтому должна обрабатываться отдельно.

При заявленном размере payload больше `kMaxFramePayloadSize` текущий кодек
отбрасывает первый байт сигнатуры и продолжает искать следующий кадр, не ожидая
весь чрезмерно большой payload и не формируя ответ. Иной диагностический ответ
невозможен без отдельного правила пропуска такого кадра, потому что кодек не
может сохранять произвольный объём данных только ради проверки CRC.

## Переполнение очереди

Для локальной очереди применяются следующие правила:

1. Немедленно сформировать `queue_full` вне очереди и отправить его активным
   транспортом. Для внутренней команды постановка возвращает `false`, а её
   производитель решает, повторять ли попытку.
2. Один из восьми слотов зарезервирован для `SendTransportResponse`. Обычные
   события получают `queue_full` уже при семи занятых слотах.
3. Существующие события не вытесняются и не отбрасываются.

Если кодек не может поставить готовое событие в очередь, Serial-транспорт
немедленно отправляет `queue_full`, не создавая ещё одно событие.

Диспетчер сначала извлекает запрос и освобождает слот. Для синхронного ответа
доступен этот слот, а для асинхронного ответа дополнительно гарантирован
зарезервированный восьмой слот. Другие задачи и прерывания напрямую в локальную
очередь не пишут.

## Клиент и незавершённые запросы

Текущий протокол не содержит идентификатора запроса, поэтому одновременно может
существовать только один незавершённый клиентский запрос:

```text
отправить запрос
→ дождаться ответа или тайм-аута
→ разрешить отправку следующего запроса
```

Клиент должен обеспечивать это правило не только блокировкой обмена, но и своим
состоянием интерфейса, чтобы пользователь не запускал новую операцию во время
ожидания ответа. Добавление нескольких одновременных запросов потребует
идентификатора запроса в прикладном протоколе и не входит в текущую
реорганизацию.

## Асинхронная обработка

Операция `set` уже завершается не в том же вызове, в котором принят запрос.
Диспетчер хранит одну незавершённую транзакцию; это соответствует действующему
ограничению клиента на один запрос. Будущее измерение сможет использовать ту же
модель:

```text
ProcessTransportRequest
→ StartMeasurement
→ ProcessAcquiredData или ProcessStoredSweep
→ SendSweepData или SendStoredSweep
```

Штатная остановка будущего измерения должна завершить текущий sweep. Ошибка ADC
или `overrun` отбрасывает незавершённый sweep, переводит измерительный процесс в
`Fault` и требует явной команды восстановления; скрытый автоматический повтор
не используется.

## Бинарные графики и размер кадра

Одна точка графика с 16-битными координатами X и Y занимает 4 байта. Поэтому
сырые данные графика занимают:

| Число точек | Размер |
| ---: | ---: |
| 100 | 400 байт |
| 200 | 800 байт |
| 300 | 1200 байт |
| 400 | 1600 байт |
| 500 | 2000 байт |

При небольшом восьмибайтном заголовке sweep в транспортный payload размером
2048 байт помещается 510 таких точек. Следовательно, график из нескольких сотен
точек не требует сверхдлинного сообщения, если передавать его в бинарном виде.

Для бинарного результата одиночного sweep используется тип пакета 2. Это
обычный кадр с пределом payload 2048 байт, а не часть автоматически
фрагментируемого длинного пакета.

Автоматическое дробление сверхдлинных сообщений пока не вводится. Если sweep
перестанет помещаться в один кадр, предпочтительный вариант — хранить его во
Flash и добавить прикладную команду запроса конкретного фрагмента. Каждый
бинарный фрагмент должен самостоятельно содержать идентификатор sweep, номер
или смещение фрагмента, общее число точек либо фрагментов и число точек в этом
кадре. Это позволит клиенту точечно повторно запросить, например, третий
фрагмент без скрытого состояния в кодеке.

## Конфигурация

Хранение и проверка конфигурации отделяются от транспорта. Измерительный модуль
получает настройки через независимый интерфейс и не зависит от Serial-протокола.

При выполнении `set` диспетчер координирует межъядерную транзакцию:

1. Собрать конфигурацию-кандидат.
2. Проверить типы и допустимость значений.
3. Отправить `PrepareConfig` на Core 0. Сейчас команда применяется сразу в
   состоянии `Idle`; после реализации сбора она будет ждать границы sweep.
4. После `ConfigPrepared` оставить измерительную задачу в состоянии ожидания и
   сохранить кандидата в NVS на Core 1.
5. При успешном сохранении отправить `CommitConfig`, дождаться
   `ConfigCommitted`, опубликовать конфигурацию и вернуть успешный ответ.
6. При ошибке сохранения отправить `RollbackConfig`, дождаться результата и
   вернуть `storage_error`. До commit или rollback новый sweep не запускается.
7. При ошибке prepare восстановить прежнюю аппаратную конфигурацию на Core 0 и
   вернуть `configuration_apply_error`. Неудачный откат переводит
   `AcquisitionTask` в `Fault`.

Если `PrepareConfig` не помещается в управляющую очередь, состояние не меняется,
а клиент получает существующую ошибку `queue_full`. Код
`acquisition_busy` не вводится: активный sweep является нормальным состоянием,
и команда ждёт его границы.

Дополнительные смысловые ограничения полей, отсутствующие сейчас, в рамках этой
реорганизации не вводятся.

## Открытые решения

- Нужно ли менять текущее молчаливое восстановление синхронизации при
  заявленной длине payload больше установленного предела.
- Точные форматы payload команд сырых данных и ссылок на sweep во Flash.
- Формат хранения sweep во Flash и политика освобождения записей.
- Постоянная серия sweep, хранение результатов во Flash и формат запроса
  фрагментов; текущий одиночный sweep передаётся одним кадром типа 2.
- Поведение при переключении транспорта после появления второго транспорта.
